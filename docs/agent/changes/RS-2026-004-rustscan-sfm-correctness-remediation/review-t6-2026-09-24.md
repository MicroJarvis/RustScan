## P2 — Transaction cleanup masks the original failure

Location: `rustscan-sfm/src/io/database.rs:1025-1041`, reused by the new
transaction wrappers, including `ColmapDatabase::merge` at line 666.

The existing helper was reused unchanged, but the T6 instruction explicitly
required auditing it and preserving write/commit/rollback errors. On operation
failure, a failed explicit ROLLBACK replaces the original error. SQLite can
already have rolled back the transaction (for example RAISE(ROLLBACK), or
certain database errors), so this is a reachable error-reporting defect.
The commit-failure branch also explicitly discards the ROLLBACK result.
The handoff claim that all three error kinds propagate is therefore incorrect.

Independent public-API reproduction: merge a source with two cameras into an
empty target. A target trigger raises ROLLBACK on the second camera, after the
first insert succeeds. The target contains zero cameras afterwards, but the
returned error chain is only:

```text
roll back COLMAP database transaction: cannot rollback - no transaction is active
```

The original `t6-original-second-camera-failure` is absent. The assertion that
the original error survives fails with exit 101. This proves lost diagnostics,
not leaked rows. Probe source and output are under
`artifacts/runs/t6-independent-review/rollback-error-probe.rs` and
`rollback-error-probe.log`; no product source was modified.

Required action: recognize an already-ended transaction, preserve the original
operation or commit error, and include any actual cleanup failure without
silently discarding either error. Restore deletion bookkeeping consistently
with the transaction outcome. Add deterministic automatic-rollback and
commit-failure regressions, including successful reuse of the connection after
successful cleanup. Keep any injected failure mechanism test-only.

## P2 — Rollback evidence does not cover the requested logical contents

Locations: `rustscan-sfm/src/io/database.rs:5752-5797` and merge regressions;
`rustscan-sfm/src/sfm/mapper.rs:19433-19604`, `20315-20477`.

`LogicalDbSnapshot` captures counts, camera IDs and image names, but omits most
payloads and reference relationships. The merge fixtures fail during camera /
image population, before frames, priors, matches and geometries are written.
The population fixtures fail at descriptor insertion, before the pair phase;
they check selected counts and one old keypoint payload. The deletion test
directly calls `with_transaction` and does not exercise the business entry
points. Its initial deletion flag is only false. Retry assertions largely
check counts/existence rather than the expected complete contents.

These tests catch the original absence of a transaction (the recorded pre-fix
failures confirm that), but do not meet the explicit full-content snapshot,
late-write rollback, bookkeeping and retry acceptance requirements. No row
leak in those untested paths is claimed by this review.

Required action: use populated fixtures and deterministic logical snapshots
of all affected table rows, including IDs, references and payloads. Inject a
late failure through population and merge after their pair/relationship writes
have executed; compare the complete target before/after and check complete
expected contents on retry against the same target. Retain the useful existing
pair update-then-insert regression and extend its retry payload checks. Cover
deletion bookkeeping preservation from both false and true initial states,
using actual deletion paths where reachable. Do not add production test APIs.
